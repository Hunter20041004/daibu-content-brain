# 新創公司資格查證設計

日期：2026-08-10

## 背景

「AI 新創介紹」目前只驗證候選有具體公司名稱、HTTPS 來源與可核對引文，沒有驗證公司是否仍是新創。因此成立於 2009 年、2019 年已上市的 Cloudflare 仍能成為候選。

這和前一輪排重是不同問題：排重回答「以前介紹過沒有」，本輪資格查證回答「它現在是否符合這個系列」。只在 prompt 裡加一句「不要上市公司」仍可能被生成式 AI 忽略，因此要用搜尋證據與程式規則共同判定。

## 已確認的產品規則

公司必須同時符合以下三項才可進入「AI 新創介紹」：

1. 尚未公開上市。
2. 仍是獨立公司，不是已被收購的公司或母公司的子公司。
3. 依成立年份計算不超過 10 年；只有年份時採 `目前年份 - 成立年份 <= 10`。

資料不足、來源互相矛盾或無法核對時，一律視為未知並排除，不讓 AI 猜測。

## 使用者結果

- 現有 Cloudflare 候選保留在 SQLite，但不再顯示。
- 現有 Moove 與 Railway 用同一套自動查證流程回補資格；只有通過才繼續顯示。
- 按「再產生 3 則」時，候選通過來源驗證與排重後，才進行新創資格查證；不合格者不寫入 `ideas`。
- 找不到三家合格公司時寧可少產，不放寬條件，也不為湊數反覆呼叫 API。
- 若搜尋或判定服務失敗，畫面說明資格查證沒有完成，原有資料不受影響。

## 採用方案

採「每家公司一次 Tavily 搜尋，整批一次免費 LLM 判定，程式最後硬性驗證」的三段式流程。

### 為何不用另外兩種方案

- **只改 prompt**：沒有額外搜尋成本，但 AI 可能依印象誤判或忽略條件，無法解決本次根因。
- **維護成熟公司黑名單**：能立刻擋 Cloudflare，卻必須永遠人工補名單，下一家上市公司仍會漏過。

採用方案每批最多增加 3 次 Tavily 搜尋與 1 次目前啟用的免費 LLM 呼叫；預設是 Gemini。這是使用者已確認的速度與免費額度取捨。

## 資料結構

新增 `company_eligibility` 表，依正規化公司名保存最近一次查證：

- `company_key`：去頭尾空白並忽略大小寫後的公司名，主鍵。
- `company`：顯示名稱。
- `verdict`：`eligible`、`ineligible` 或 `unknown`。
- `founded_year`：可核對的成立年份，未知時為 null。
- `ownership_status`：`private_independent`、`public`、`acquired` 或 `unknown`。
- `reason`：給使用者看的短原因。
- `evidence_json`：實際採用的來源網址、逐字引文與支持的 claim。
- `checked_at`：查證時間。

不修改 `ideas` 的既有欄位，不刪除候選。資格紀錄和內容候選分開，是因為同一家公司的上市／收購狀態是公司層級事實，不是某一篇文章的內容。

## 資料流

```text
素材產生公司候選
  → 既有來源與排重檢查
  → 每家公司各做 1 次 Tavily 資格搜尋
  → 整批資料交給 Gemini 判定
  → 程式核對年份、狀態、網址與逐字引文
  → 保存公司資格紀錄
  → 只有 eligible 寫入 ideas
```

## 搜尋與判定契約

### Tavily 搜尋

每家公司只送一個查詢，目標是取得成立年份、融資／私人公司證據、IPO／股票代號、收購或母公司證據。每家最多 5 筆 HTTPS 結果。

搜尋結果只是證據候選，不能直接當結論；來源 URL 與摘要會完整交給判定器。

### LLM 回傳

整批一次回傳 JSON 陣列，每家公司包含：

- `company`
- `founded_year`
- `ownership_status`
- `reason`
- `evidence`：每筆只含 `claim`、`source_url`、`quote`

`claim` 只允許 `founded`、`private_independent`、`public`、`acquired`。不得引用模型常識。

### 程式硬性驗證

- `source_url` 必須等於 Tavily 本批實際回傳的網址。
- `quote` 必須逐字存在於對應搜尋摘要。
- 合格公司必須同時有 `founded` 與 `private_independent` 的有效證據。
- `founded_year` 必須和成立證據一致，且符合 10 年門檻。
- `ownership_status` 必須是 `private_independent` 才能合格。
- 有有效 `public`、`acquired` 或超過 10 年證據時判為不合格。
- 欄位缺漏、JSON 解析失敗、證據對不上或結論矛盾時判為未知，不寫入候選。

## 快取與重複成本

- 已有明確 `ineligible` 紀錄的公司，下次直接排除並交給 prompt 避開，不重做搜尋。
- 新候選與尚未查證的舊候選才使用 Tavily／LLM。
- 這份資格代表「選題當下是否符合新創」，不因日後上市而回頭刪除歷史內容。
- 現有頁面對沒有任何資格紀錄的舊資料維持相容顯示；正式上線前會先回補現有 Moove、Railway、Cloudflare，因此真實資料不會留在未查證狀態。
- 明確 `ineligible` 或 `unknown` 的公司在公司介紹頁隱藏；資料列仍保留。

## 舊資料回補

提供可重跑的本機 backfill 命令：

1. 只讀取公司介紹系列中尚未有資格紀錄的非空白公司。
2. 使用和新候選完全相同的 Tavily＋LLM＋硬性驗證流程。
3. 只寫入 `company_eligibility`，不修改 `ideas`。
4. 正式執行前備份 `daibu.db`；執行後直接查 SQLite，確認 ideas 的筆數與內容未變。

## 錯誤處理

- 單一公司的 Tavily 搜尋失敗：該公司標為未知，其他公司繼續。
- 整批 LLM 呼叫或 JSON 解析失敗：不建立任何新候選，顯示「公司資格查證未完成」。
- 全部候選不合格／未知：不新增空候選，原有內容維持不變。
- 缺少 Tavily 或 Gemini key：沿用設定頁提示，不降級成未查證候選。

## 測試與驗收

依垂直 TDD 完成：

1. 資料表建立、寫入、讀取與不修改 `ideas`。
2. JSON 解析、證據逐字核對、10 年門檻、上市／收購／未知判定。
3. 每家公司一次搜尋、整批一次 LLM、部分搜尋失敗與整批解析失敗。
4. selection 只保存 eligible，ineligible／unknown 不寫入。
5. 公司頁隱藏有明確不合格／未知紀錄，未有紀錄的 legacy 資料維持相容；一般系列不受影響。
6. 真實 Tavily＋Gemini 契約：Cloudflare 不合格；Moove 與 Railway 必須取得足夠證據才合格，否則誠實回報未知並修正搜尋契約，不硬改 mock。
7. 正式資料回補前後校準 ideas 仍為 10 筆；使用者畫面不再出現 Cloudflare。
8. 若畫面候選數或錯誤文案改變，依前端規範完成兩輪 1280×800 與 375×812 截圖自檢。

## 不在本次範圍

- 不處理公司別名合併。
- 不建立人工白名單／黑名單介面。
- 不自動定期重查已發內容。
- 不使用付費公司資料庫或新增供應商。
- 不刪除 Cloudflare 或其他舊候選。
