# 公司介紹候選排重與舊資料相容設計

日期：2026-08-10

## 背景

「AI 新創介紹」已設定為只產生公司介紹，但候選畫面仍混有六則沒有公司名稱的舊題目，並出現 Railway 被推薦兩次的情況。

實際資料庫校準結果：畫面顯示 10 則候選，資料庫同樣有 10 則；其中 6 則建立於公司介紹限制上線以前，`company` 為空白；其餘 4 則有公司名稱，但 Railway 出現兩次。

根因有兩個：

1. 舊候選不會因系列改成公司介紹而自動消失，介面又用「比較｜標題」替代空白公司名稱。
2. 再產生候選時，系統只把「已淘汰的標題」交給 AI 避開，沒有排除候選、已採用或已發佈的公司，也沒有在寫入資料庫前做公司層級的第二次檢查。

## 已確認的產品決策

- 公司介紹系列中，同一家公司整個系列只介紹一次。
- 曾以任何狀態出現過的公司，都不得再次成為新候選。
- 同一批 AI 回傳的多則候選也不得出現相同公司。
- 找不到足夠的新公司時，寧可少於設定數量，也不使用舊公司或通用題目湊數。
- 舊資料不刪除；公司介紹系列的畫面只顯示有效且不重複的公司候選。
- 既有同公司候選採「第一次出現者保留」：依 `created_at`、`id` 由舊到新判斷，後來的重複資料保留在資料庫但不顯示。
- 介面不再用「比較」描述候選或替代缺少的公司名稱，改成「瀏覽」與「查看」。

## 使用者結果

使用者打開「AI 新創介紹」時，只看見一家公司一則的公司介紹候選。按「再產生 3 則」後，新增內容不會重複任何過去出現過的公司；若只有兩家符合條件，就只新增兩則。

目前 10 則候選在新規則下會顯示 3 則：Cloudflare、Railway 第一次出現的候選、Moove。六則沒有公司名稱的舊題目，以及 Railway 後來出現的第二則，都只會被隱藏，不會從資料庫刪除。

## 系統設計

### 1. 讀取歷史排除名單

資料庫層新增查詢，取得同一系列所有狀態的非空白公司名稱與標題。公司名稱比對前會做保守正規化：移除頭尾空白並忽略英文大小寫；不做模糊比對，避免把不同公司誤判成同一家。

### 2. AI 產生前提醒

選題 prompt 會明確列出已出現公司與標題，要求 AI 不得再次使用。這一層能降低浪費免費 API 額度，但不能單獨當作保證，因為生成式 AI 可能不完全遵守文字指令。

### 3. 寫入前強制檢查

程式收到 AI 結果後，依序檢查：

1. 有具體公司、題目、HTTPS 來源與可在素材中核對的引文。
2. 公司不在歷史公司名單。
3. 題目不在歷史題目名單。
4. 公司與題目不和本批較早通過的候選重複。

未通過者不寫入資料庫。若全部被過濾，沿用可理解的錯誤訊息，告知這次沒有找到新的可核對公司，既有內容不受影響。

### 4. 舊資料相容顯示

公司介紹系列的候選、已採用與已發佈清單共用一個「有效公司項目」規則：缺少公司名稱的不顯示；同系列同公司只顯示最早建立的一筆。一般內容系列不套用這個限制。

資料不搬遷、不刪除、不改狀態，因此可回溯；若未來需要整理資料庫，再另做有明確備份與確認的清理功能。

### 5. 介面文案

- 「先比較公司與它在做什麼」改為「先瀏覽公司與它在做什麼」。
- 產生中的「逐則比較」改為「逐則查看」。
- 公司候選按鈕維持「公司名｜公司在做什麼」，不再出現「比較｜」。

## 錯誤與成本

- 不增加新的外部服務或付費相依。
- 本次不為補足三則而自動重試 Gemini，以免一次點擊反覆消耗免費額度。符合條件的結果有幾則就新增幾則。
- 若 AI 只回傳舊公司或不合格資料，畫面會說明沒有找到新的可核對公司，不會建立空白或重複候選。

## 測試策略

依 TDD 垂直切片完成：

1. 資料庫測試：所有狀態的歷史公司與標題都能被讀出，空白公司不進公司名單。
2. 選題測試：歷史公司、歷史標題與同批重複會在寫入前被擋下，只留下全新公司。
3. Prompt 測試：公司介紹 prompt 明確包含已出現公司與題目，一般系列維持原行為。
4. 頁面邏輯測試：舊的空白公司候選與後來的同公司資料不顯示，第一次出現者保留。
5. UI 回歸測試：候選操作文案不再出現「比較」，桌機與手機各完成兩輪截圖檢查。
6. 真實邊界測試：用 Gemini 免費層產生一次公司候選，確認回傳結構仍可解析；不把 API 是否剛好選到歷史公司當成不穩定的契約斷言。

## 不在本次範圍

- 不刪除或改寫既有候選資料。
- 不做公司別名或模糊名稱辨識，例如 `Cloudflare, Inc.` 與 `Cloudflare` 暫時可能被視為不同字串。
- 不新增手動解除公司排除的功能。
- 不改輪播圖、Logo 或文章文案產生流程。
