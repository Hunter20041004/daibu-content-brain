# 呆一布內容工作站建造故事 HTML 設計

> 日期：2026-08-05
> 讀者：幾乎不寫程式、主要用 Vibe Coding 做作品的社團組員
> 使用情境：會後收到連結，自己閱讀，不依賴現場口頭補充

## 1. 產品結果

製作一份可獨立閱讀的繁體中文單頁 HTML，說明「我怎麼把呆一布內容工作站搭出來」。讀者看完後要能回答四件事：

1. 這個工具原本要解決什麼問題。
2. 使用者、Claude 與 Codex 在建造過程中各自負責什麼。
3. 資料如何從公開來源，走到候選題目、正文與七張輪播圖。
4. 自己要做類似工具時，可以照什麼順序開始。

這不是工程文件的換皮版。主文先講畫面、決策與因果，技術細節放在「想多懂一點」的展開區塊。讀者即使不打開任何程式碼，也能理解整套建造方法。

## 2. 核心敘事

主線採「建造故事」，不是照檔案名稱介紹功能。

開場先呈現社團內容工作的真實困難：來源分散、每次重新想題、候選與正文斷開、做完後不知道哪些主題值得延續。接著說明我沒有直接叫 AI 寫一個完整網站，而是先決定範圍，把大問題拆成一段段可以驗收的產品能力。

故事中清楚區分三種責任：

- 使用者決定產品要解決什麼、哪些行為不能接受，以及最後看起來是否真的好用。
- Claude 協助釐清需求、比較方案、寫設計規格與實作計畫。
- Codex 依計畫寫測試、實作、操作驗收並修正問題。

這段不把 AI 描述成自動完成一切的魔法。文件要讓讀者看到，Vibe Coding 的難點不是把需求打進聊天框，而是做決定、切範圍、保護資料，以及確認結果。

## 3. 閱讀結構

### 3.1 封面：一句話看懂成果

- 標題：「我怎麼用 Vibe Coding 搭出呆一布內容工作站」
- 副標：從一個選題痛點，做成能找公司、寫正文、產七張輪播圖的本機工具。
- 標示約 10–15 分鐘閱讀時間。
- 用簡化的工作台示意與呆一布吉祥物建立第一眼辨識，不放程式碼。

### 3.2 起點：我們原本卡在哪裡

用 Before / After 流程並排：

- 過去：四處找資料 → 臨時想題 → 文件散落 → 做完沒有回顧。
- 現在：找題材 → 選一則 → 寫內容 → 做輪播 → 回填成效。

這一章只講使用者看得到的改變，讓讀者先知道為什麼值得做。

### 3.3 分工：我不是把整件事交給 AI

以三欄角色卡呈現使用者、Claude、Codex 的工作，旁邊放一條小迴圈：

需求與限制 → 設計與計畫 → 測試與實作 → 操作驗收 → 回到下一輪決策。

第一次出現「規格」與「測試」時，用日常比喻解釋：規格像裝潢前的施工圖；測試像先寫好驗收清單，避免完工後才發現門打不開。

### 3.4 系統地圖：六個角色怎麼合作

用 HTML 與 CSS 畫架構圖，不用 ASCII 圖。由左到右呈現：

1. Streamlit：使用者看到的櫃台。
2. Python 核心邏輯：處理規則的廚房。
3. SQLite：放主題、候選、正文與成效的本機資料櫃。
4. RSS 與 Tavily：去公開網站找材料的採購員。
5. Gemini：依材料整理候選與草稿的文字助手。
6. Playwright：把七頁 HTML 逐張拍成固定尺寸 PNG 的攝影機。

每個名詞第一次出現依「白話 → 精準定義 → 在產品裡負責什麼」三層說明。程式碼只在展開區塊放一小段，不讓主文中斷。

### 3.5 一筆內容的旅程

做成可點擊的七步驟資料流：

公開來源 → 公司研究 → 候選題目 → 人工採用 → AI 正文 → 七頁草稿 → PNG 與 ZIP。

點選任一步，右側更新三項資訊：這一步收到什麼、做了什麼、產出什麼。手機版改成垂直步驟，不產生橫向捲動。

這章同時說清楚兩個安全邊界：AI 只能依已蒐集的來源寫內容；Logo 候選必須經人確認，不能因為網址看起來像官網就自動採用。

### 3.6 真實建造時間軸

時間軸保留七個重要階段，不逐筆列 Git 提交：

1. 先做本機 v1：資料庫、來源抓取、AI 選題、狀態與成效。
2. 把外部服務包成可替換的介面，免費 Gemini 為主、Groq 為備援。
3. 從四頁表單改成以主題為核心的工作台。
4. 真人操作驗收找出 24 個問題，其中 4 個會破壞資料或讓內容消失。
5. 加入公司研究、可信來源與正文生成。
6. 加入七頁輪播草稿、品牌模板、PNG 與 ZIP。
7. 收斂成單一「AI 新創介紹」系列，完成可展示的內容工作站。

每個階段只回答三題：當時遇到什麼、做了什麼決定、產品因此變成什麼。

### 3.7 我怎麼避免 AI 一次寫歪

用一個具體例子解釋 Red → Green → Refactor：

- Red：先寫「刪除主題時，底下題目也必須刪除」的驗收條件，確認目前做不到。
- Green：只寫剛好能讓這個條件通過的程式。
- Refactor：在測試保護下整理命名與重複邏輯。

白話比喻是「先做一個會響的煙霧警報器，再開始修電線」。同一區另放 Mock 與真實邊界測試的差異：排練時朋友假裝是外送員，不代表真實外送平台一定能送到；所以 RSS、搜尋、Gemini 與瀏覽器都要另外跑真實測試。

### 3.8 踩坑與改變方法

用五張錯誤學習卡呈現，不寫成英雄敘事：

- 早期設計塞入守門線分數、來源分層與內容分類，實際使用後發現增加負擔，後來刪掉。
- 99 個測試全綠，真人仍找到 4 個會弄壞資料的問題；單元測試沒有涵蓋跨頁面與跨資料表流程。
- 測試不能直接碰真實資料庫；手動驗收一律使用 `/tmp` 複本。
- LLM 的假資料測試通過，不代表免費模型真的會照格式回傳，因此要跑契約測試。
- 出圖成功不等於畫面正確；每輪都要用桌機與手機截圖看使用者真正會看到什麼。

### 3.9 組員可以照做的建造公式

收尾提供可複製的八步驟清單：

1. 先寫一個真實痛點，不要先選技術。
2. 畫出使用者從開始到完成的一條流程。
3. 明確寫出這一版不做什麼。
4. 請 AI 比較方案並寫規格。
5. 把功能拆成一次能驗收一件事的小切片。
6. 每一片先寫失敗測試，再做最小實作。
7. 用真實畫面與真實外部服務驗收。
8. 把使用時發現的問題放回下一輪，而不是硬守初版設計。

最後一句回到使用者角色：Vibe Coding 可以把做軟體的門檻降低，但產品判斷、資料安全與驗收仍由人負責。

## 4. 視覺方向

視覺沿用現有呆一布品牌，而不是另造一套報告風格：

- 頁面底色 `#E9F6FF`
- 主要品牌色 `#6FC1CC`
- 標題與連結 `#32738F`
- 主要文字 `#0E0E2C`
- 重點底色 `#F8C0A0`
- 卡片 `#FAFCFE`，邊框 `#C7E2EA`
- 字體採 Figtree 與 Noto Sans TC，中文內文至少 16px。

吉祥物使用專案內既有 SVG，直接嵌入 HTML，避免分享後圖片路徑失效。主要視覺採編輯式長文與流程圖，不把所有內容切成等大的卡片網格。

## 5. 互動與響應式

- 桌機左側有章節導覽，手機改為頂端可捲動的章節捷徑。
- 頂端有閱讀進度條；使用者捲動時只更新 `transform`，避免版面重排。
- 專有名詞與程式碼補充使用原生 `details` / `summary`，即使 JavaScript 失效也能閱讀。
- 七步驟資料流可點擊切換，按鈕具備鍵盤焦點與 `aria-selected` 狀態。
- 互動按鈕至少 44px，高亮不能只靠顏色，需同時有文字或圖形狀態。
- hover 與按壓回饋控制在 160–220ms；減少動態偏好開啟時取消位移，只保留顏色變化。
- 提供列印樣式，列印時展開所有技術補充並移除固定導覽。
- 依 HTML Visualizer 規範保留全頁評論工具，方便收到連結的人針對段落留下意見。

## 6. 技術交付

- 最終檔案：`docs/2026-08-05-我怎麼用-vibe-coding-搭出呆一布內容工作站.html`
- 單檔 HTML，不需要專案 build 流程。
- 使用 Tailwind CDN，主要設計代幣與版面樣式仍寫在檔案內，確保可控。
- 不從外部讀取 API、資料庫或私密內容。
- 主要內容不放本機絕對路徑、API key、真實資料庫內容或只在作者電腦有效的連結。
- 資料流圖、時間軸、工作台示意都用 HTML / CSS / SVG 組成，不使用 ASCII 圖。

## 7. 風險與處理

| 風險 | 處理方式 |
| --- | --- |
| 技術內容太難 | 主文先講使用畫面與比喻，精準定義與小段程式碼漸進展開 |
| 文件太長 | 開場先給一分鐘摘要，提供章節導覽與 10–15 分鐘閱讀預期 |
| 看起來像宣傳文 | 保留設計刪除、測試漏網與資料安全等真實挫折，不誇大 AI 能力 |
| 分享後資產失效 | 吉祥物與必要 SVG 內嵌；不依賴本機檔案路徑 |
| 手機流程圖爆版 | 375px 採垂直步驟；驗收時檢查 `scrollWidth === clientWidth` |
| 動效干擾閱讀 | 動效只用於進度與操作回饋，並支援 `prefers-reduced-motion` |

## 8. 驗收標準

### 8.1 內容

- 不看程式碼也能說明工具的問題、分工、資料流與建造順序。
- Streamlit、Python、SQLite、RSS、Tavily、Gemini、Playwright、TDD、Mock、契約測試第一次出現都有白話解釋。
- 建造時間軸與現有規格、`STATUS.md`、`HANDOFF.md`、Git 提交紀錄一致。
- 不再使用的守門線、來源分層與常青／時效分類必須明說「後來移除」，不能寫成現有功能。
- 文字完成後依 `humanizer-zh` 與 HTML Visualizer 的中英混雜詞清單審稿。

### 8.2 功能與無障礙

- 所有章節連結、展開區塊、資料流按鈕與評論工具可用。
- 鍵盤可以走完所有互動元件，焦點框清楚可見。
- 正常文字對比至少 4.5:1。
- JavaScript console 無錯誤。
- 375px 寬度沒有橫向捲動。

### 8.3 視覺

依專案前端規範跑至少兩輪：

1. 1280×800 桌機截圖一張。
2. 375×812 手機截圖一張。
3. 每輪逐項檢查層次、留白、字體、配色、對齊、響應式、互動狀態與動效。
4. 第一輪明確列出不合格項目並修正。
5. 第二輪全部通過後，把最終截圖路徑記入 `HANDOFF.md`。

## 9. 不做

- 不修改 Streamlit 產品功能、資料表或 AI 指令。
- 不重新錄製影片或呼叫 Tavily、Gemini。
- 不把文件做成投影片、正式官網或需登入的線上服務。
- 不用大量程式碼證明技術深度。
- 本輪只交付可分享的 HTML；實際上線到公開網址不在本規格內，除非專案已有可沿用的正式部署流程。
