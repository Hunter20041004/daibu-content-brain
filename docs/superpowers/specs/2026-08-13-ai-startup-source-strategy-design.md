# AI 新創介紹來源策略重整設計

日期：2026-08-13

## 背景與根因

「AI 新創介紹」目前綁定 `Y Combinator Blog` 與舊 `a16z` RSS。實際查核顯示：

- `https://a16z.com/feed/` 已回傳 HTTP 404。
- YC Blog 雖可讀取，但最新公司文章集中在 IPO；EquipmentShare、Meesho、Groww、
  BillionToOne 都是上市消息。
- 因此第一階段 LLM 從來源中推薦公司，第二階段新創資格查核又把同一批上市公司排除，
  形成「有讀到資料、卻產不出新候選」的結構性衝突。

本輪不放寬既有資格規則。成立不超過十年、未上市、未被收購且仍為私人獨立公司，
仍是「AI 新創介紹」的產品定義。要修的是資格審查之前的公司發現來源。

## 使用者結果

- 按「再產生 3 則」時，系統優先從最近推出的 AI 公司與早期 AI 加速器公司中找新公司。
- 每批目標為 3 則：2 則來自公司目錄，1 則來自近期新創新聞；不足時寧可少產。
- 已上市、已被收購、超過十年、已出現或資料不足的公司仍不建立候選。
- 畫面要能分辨「來源暫時讀不到」、「公司都重複」、「資格不符」與「外部 API 失敗」，
  不再全部顯示成同一句錯誤。
- 既有候選、正文、來源快照與資格查核紀錄不刪除、不重寫。

## 已採用方案

採用「公司目錄負責找誰、新聞來源負責回答為什麼現在、既有資格查核負責最後把關」
的混合來源架構。

```text
YC Launches + a16z Speedrun Companies
  → 找近期、早期且 AI 相關的公司
  → YC Companies 公司頁／Speedrun 當期目錄資料補成立年份、狀態、官網與分類
  → 排除歷史重複與目錄已明示 Public / Acquired 的公司
  → TechCrunch Startups 補近期事件與選題理由
  → 既有 Tavily + 免費 LLM 資格查核
  → 程式核對證據
  → 最多建立 3 則候選
```

### 不採用的方案

1. **保留目前兩個 RSS，只加關鍵字排除 IPO**
   - 優點：改動最少、幾乎沒有新增外部請求。
   - 缺點：a16z 已失效；YC Blog 最新內容本來就沒有足夠的私人 AI 新創，排除 IPO 後仍可能是零。

2. **把所有現有來源全部綁進系列**
   - 優點：素材量看起來最大。
   - 缺點：iThome、模型官方新聞、Reddit、GitHub、Product Hunt 等回答的是不同問題，
     會增加雜訊、重複與免費 LLM 判讀成本，不能保證得到可查核的公司。

3. **只用公司目錄，不讀近期新聞**
   - 優點：候選公司穩定、資格欄位完整。
   - 缺點：只能回答「這家公司是誰」，較難回答「為什麼現在值得介紹」。

混合方案多了少量公開頁面請求與解析維護成本，但最符合「新公司＋近期理由＋可查證」的產品目標。

## 來源取捨

### 新增並綁定「AI 新創介紹」

| 來源 | 角色 | 使用規則 |
|---|---|---|
| YC Launches | 近期公司發現主來源 | 讀最新發佈，保留有 AI／Machine Learning 相關標籤的公司；先排除已出現公司 |
| a16z Speedrun Companies | 早期 AI 公司發現主來源 | 優先最新 cohort，保留 AI Agents、AI Infra、AI Models / Research、AI Voice、AI Generative Media 等 AI 分類 |
| YC Companies | YC 公司資料補強 | 讀成立年份、batch、官網與狀態；`Public`、`Acquired` 直接排除，`Active` 仍須走最終資格查核 |
| TechCrunch Startups | 近期事件輔助 | 只讀 Startups feed 中帶 AI 的文章；IPO、收購與純爭議消息不可成為合格公司線索 |

公開頁面在 2026-08-13 的邊界查核結果：

- YC Launches 回傳結構化 JSON；最新頁每頁 20 筆，含公司名稱、官網、標籤、batch、發佈時間與來源頁。
- YC Companies 公司頁可讀成立年份與 `Active / Public / Acquired` 狀態。
- Speedrun 公開目錄資料已可一次讀到 cohort、成立年份、團隊人數、AI 分類、官網與公司介紹；無需逐家開詳情頁。
- TechCrunch Startups RSS 可讀，且文章帶 `AI`、`Startups`、`Fundraising` 等分類標籤。

### 既有來源處置

| 既有來源 | 處置 | 理由 |
|---|---|---|
| Y Combinator Blog | 保留、維持啟用、解除本系列綁定 | 網址正常，適合 YC 生態新聞，但不適合持續找私人 AI 新創 |
| 舊 a16z RSS | 保留紀錄、解除綁定、停用 | URL 已 404；不可改名或改網址冒充 Speedrun，兩者是不同來源 |
| TechCrunch 綜合 RSS | 原樣保留、不綁定 | 來源庫可能供其他系列使用；另建較精準的 TechCrunch Startups |
| 其他 13 個既有來源 | 全部原樣保留、不自動綁定 | 它們各有用途，但不是本系列的公司發現主來源 |

不刪除來源紀錄，是為了保留使用者設定與日後復用可能；不修改舊來源身分，是為了讓歷史可追溯。

## 技術邊界與資料模型

目前 `Material` 只有文章標題、網址與摘要，無法安全承載公司狀態。新增獨立的
`CompanyLead`（公司線索）資料結構：

- `company`：公司名稱。
- `description`：目錄或新聞提供的公司描述。
- `discovery_url`：找到公司的公開頁面。
- `profile_url`：目錄內的公司詳情頁，可為空；不與 launch 或新聞網址混用。
- `official_url`：目錄提供的公司官網，可為空。
- `founded_year`：目錄明示的成立年份，可為空。
- `ownership_status`：`active`、`public`、`acquired` 或 `unknown`。
- `batch_or_cohort`：YC batch 或 Speedrun cohort，可為空。
- `tags`：AI 與產業分類。
- `published_at`：Launch 或新聞時間，可為空。
- `source_name`：來源名稱。

`CompanyLead` 只是「值得進一步查」的線索，不直接等於合格候選，也不取代
`company_eligibility` 的證據紀錄。

來源庫新增「公司目錄」抓取類型。公司目錄由程式內的白名單 adapter 解析：

- YC Launches adapter
- YC Companies adapter
- Speedrun Companies adapter

adapter 只接受設計中核可的公開 URL；任意網站不能只選「公司目錄」就執行自動解析。
RSS 與網域搜尋維持原本行為。介面以白話顯示「RSS／網域搜尋／公司目錄」，不暴露內部類別名稱。

## 候選組合與資料流

每次產生依序執行：

1. 讀 YC Launches 最近 40 筆，依 AI 標籤與時間排序。
2. 讀 Speedrun 目錄，優先最高 cohort 且帶 AI 分類的公司。
3. 讀本系列歷史公司、標題與 `company_eligibility` 快取，先排除重複、`ineligible` 與 `unknown`。
4. YC 公司線索以 YC Companies 詳情補成立年份與狀態；Speedrun 線索直接使用當期目錄內的結構化欄位。
5. 目錄明示 `Public` 或 `Acquired` 時直接排除；`Active` 或沒有狀態不能直接視為合格。
6. 從 TechCrunch Startups 最近 20 篇中保留同時帶 AI 與 Startups 的文章，排除 IPO、完成收購與純爭議事件。
7. 建立最多 2 個目錄線索＋1 個近期新聞線索；同家公司只保留一次。若新聞線索不足，
   可由目錄補足；若目錄不足，不為湊滿而使用不合格新聞。
8. 免費 LLM 只負責把通過前置篩選的線索整理成 title、angle、source URL 與逐字引文，
   不可憑模型記憶新增公司。
9. 沿用既有 Tavily＋整批免費 LLM＋程式硬性證據核對，只有 `eligible` 寫入 `ideas`。

## 成本與快取

- 公司目錄與 RSS 本身不需要新 API key，也沒有訂閱費。
- YC Companies 詳情只查本批真正可能使用的公司；Speedrun 只讀目錄頁與最新 cohort 的一批結構化資料，不掃完整歷史目錄。
- 既有公司排重與資格快取要在詳情頁與 Tavily 前執行，避免浪費網路請求與免費額度。
- 每家公司仍最多一次 Tavily 資格搜尋；整批仍只做一次資格判定 LLM。
- 不為湊滿 3 則反覆呼叫免費 LLM。
- 本輪不新增排程或背景爬蟲；只有使用者按下產生時才讀公開來源。

## 錯誤與可觀察性

「可觀察性」白話是讓系統留下足夠線索，日後能看出卡在哪一關，而不是只看到「失敗」。

每次產生要記錄一筆不含 API key、全文 prompt 或完整網頁內容的摘要：

- 各來源取得幾筆、耗時與失敗類型。
- AI 標籤篩選後剩幾家。
- 歷史重複、目錄狀態、新聞類型與資格查核各排除幾家。
- 免費 LLM 是否為 429、503、timeout 或格式錯誤。
- 最終建立幾則候選。

使用者訊息分開處理：

- 單一來源失效：其他來源繼續；顯示哪個來源暫時讀不到。
- 全部發現來源失效：不呼叫 LLM，顯示「目前沒有可用的公司來源」。
- 公司全重複：顯示「這批來源裡的公司都介紹過了」。
- 公司全因上市／收購／年齡被排除：顯示「找到公司，但沒有符合本系列資格的公司」。
- Gemini 429／503／timeout：顯示友善的 API 狀態，不輸出底層英文錯誤。
- 任一失敗都不刪除或覆寫原有候選。

## 舊資料與正式資料遷移

- 不刪除或修改任何 `ideas`、正文、狀態、`idea_sources`、`carousel_sources` 或輪播內容。
- 不刪除任何 `company_eligibility` 紀錄；既有不合格／未知公司繼續用來排重與節省成本。
- 舊 a16z 來源只更新為停用並解除 `theme_sources` 綁定，資料列保留。
- YC Blog 只解除本系列綁定，來源本身仍啟用。
- 其他既有來源不變。
- 新來源以可重跑且不重複的 migration／seed 更新加入；使用者曾刪除的無關預設來源不補回。
- 正式資料修改前先備份 SQLite，並用已知的 10 筆 ideas 與目前可見 2 則候選校準查詢；修改後再次驗證內容指紋與可見候選不變。

## TDD 與驗收

嚴格依垂直切片 Red → Green → Refactor，一次一個失敗測試：

1. `CompanyLead` 與來源 adapter 契約；先測 YC Launches 一筆映射，再做最小實作。
2. YC Companies 狀態與成立年份；先重現 Public 公司未能前置排除，再實作。
3. Speedrun 目錄與當期結構化資料；先測 AI 分類、cohort、成立年份與官網。
4. TechCrunch Startups 標籤與 IPO／收購排除；一次補一種行為。
5. 歷史排重在詳情與 Tavily 前發生，驗證不需要的外部呼叫為零。
6. 2 個目錄＋1 個新聞的組合，並測不足時少產與新聞不足時由目錄補足。
7. 每一種錯誤訊息與安全 log；確認不含 API key、prompt 或完整網頁內容。
8. 來源遷移：舊 a16z 停用、YC Blog 解除綁定、新來源加入、其他來源與舊內容不變。
9. 真實邊界測試分別打 YC Launches、YC Companies、Speedrun 與 TechCrunch Startups，
   驗證實際欄位與狀態；公開頁格式與 mock 不一致時修實作，不調 mock 假通過。
10. 以正式資料庫副本跑完整產生流程，至少能建立 1 家新的合格候選；若公開資料當下確實不足，
    必須從分段 log 證明原因，不以放寬資格門檻換取綠燈。
11. 全套 pytest 通過；合併 main 後重跑全套。
12. 因畫面會新增來源類型與分流錯誤訊息，依前端規範完成兩輪 1280×800 與 375×812 截圖自檢，
    並實際操作一次「再產生 3 則」。

## 安全、限制與不在本次範圍

- 只讀公開頁面，不登入、不繞過網站限制、不保存個人資料。
- 不使用付費公司資料庫、不新增付費 API、不更換既有免費 LLM 策略。
- 目錄頁可能改版，因此真實契約測試與來源失效 log 是必要保護，不能把 HTML 結構視為永遠不變。
- YC／Speedrun 自述資料可作為公司線索與前置排除依據，但 `Active` 不等於已證明私人獨立，
  最終仍由跨來源資格查核把關。
- 不做自動排程、全目錄鏡像、公司別名介面或人工白名單／黑名單介面。
- 不回頭刪除或改寫已發內容。
