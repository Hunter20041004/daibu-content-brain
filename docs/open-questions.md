### Streamlit 雙模式圖表色盤

2026-07-24 實測 Streamlit 1.60：`chartCategoricalColors` 只能放在共用 `[theme]`，
放在 `[theme.light]`／`[theme.dark]` 會出現「not a valid config option」警告。因此
先共用品牌藍綠、次級藍、Highlight 三色；若未來需要各自最佳化深色圖表，再改由圖表

### Streamlit 手動配色模式沒有穩定的 DOM 屬性

2026-07-25 實測 Streamlit 1.60：從右上選單手動切換 Light／Dark 時，`.stApp` 的
`color-scheme` 計算值與 Emotion 產生的 class 會改變，但 `html`、`body`、`.stApp`
都沒有 `data-theme` 或其他可供自訂 CSS 穩定判斷的屬性；`#portal` 仍是
`color-scheme: normal`。`st.context.theme.type` 是正式介面，但官方文件也警告它在
使用者切換主題時可能慢一個重跑才更新。

本輪以三層方式處理：`prefers-color-scheme` 當系統預設備援、`st.context.theme.type`
當伺服器端覆寫，並用瀏覽器實測的 Streamlit 1.60 Light／Dark Emotion class 讓
`body:has(...)` 在切換當下同步 `.stApp` 與 `#portal`。最後一層會受 Streamlit
版本影響；未來升級 Streamlit 時，必須重跑深淺模式的全部彈窗截圖，若 class 改名就
更新對應值。若 Streamlit 日後提供穩定的 `data-theme`，應改用正式屬性並移除
Emotion class 相依。

### 舊 schema 欄位名稱的驗收規則

完工清單要求全 repo 搜尋 `gate_score`、`source_layers` 等舊名稱時只能剩 `docs/`，

### ~~Logo 檔案大小與像素上限~~ — 已裁決（2026-07-30）

2026-07-30 Phase B 已要求 PNG 必須可完整解碼且帶透明資訊，SVG 也會阻擋腳本、
事件、樣式與檔案外部引用；但設計規格沒有定義單一 Logo 的檔案大小或最大像素。

**裁決**：檔案大小與解碼後像素分開限制。

| 限制 | 值 |
|---|---|
| 檔案大小（SVG 與 PNG 共用） | ≤ 2 MB |
| PNG 單邊 | ≤ 4096 px |
| PNG 總像素 | ≤ 8,000,000 px |
| PNG 單邊下限 | ≥ 64 px |
| SVG 結構 | 必須有 `viewBox`，或同時有 `width` 與 `height` |

理由摘要：官方素材幾乎都遠低於 2 MB，這條線剛好擋掉誤傳的照片與截圖；但檔案
大小騙得了人——壓縮後 500 KB 的 PNG 解開可能是 10000×10000、吃掉 400 MB 記憶體
（解壓縮炸彈），所以要再限解碼後的像素。4096 px 對實際只顯示約 300 px 寬的封面
Logo 已是 13 倍餘裕；64 px 下限擋的是誤傳的 favicon。Pillow 預設上限 89 MP 對這
個用途太寬鬆，實作時要把 `MAX_IMAGE_PIXELS` 一起壓到 800 萬。

這五條**只在新的 `validate_upload()` 執行**，不動既有 `logo_data_uri()`／
`_validate_svg()`：後者是安全檢查，且既有綠燈測試用的 SVG 沒有 viewBox。

完整理由、錯誤文案與實作要求：
`docs/specs/2026-07-30-來源蒐集與出圖接線-design.md` §5.2、§5.3。

## 2026-07-30 這一輪新增的未決事項

### 抓網頁不做內網位址阻擋

`daibu/fetch/page.py` 會下載使用者貼上的任意 https 網址。目前只做
「https、15 秒 timeout、最多讀 1 MB、只抽純文字」，**不阻擋指向內網或
localhost 的位址**。前提是這是本機單人工具，貼網址的人就是使用者自己。

若日後改成多人或部署上線，這就是一個 SSRF 破口，必須補上位址過濾。

### 被換掉的舊 Logo 檔不自動刪

`assets/logos/` 以「公司 slug ＋ 檔案雜湊」命名，換 Logo 時只覆蓋
`brand_assets` 那一列，舊檔留在磁碟。理由是刪錯比留著糟。長期使用後資料夾會慢慢
累積無用檔案；要不要做清理，等真的變多再說。

### 草稿的 section 增刪與來源重新指派

本輪只開放改文字，label 與 `source_ids` 唯讀。實際用過之後若發現常常需要「這段
其實引的是 S3 不是 S2」，再決定要不要開放，以及怎麼在畫面上表達才不會讓人隨手
改壞來源對應。
