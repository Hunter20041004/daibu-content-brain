# 設計規格：選題為核心的資訊架構重整

- 日期：2026-07-24
- 狀態：**已與使用者定案**（brainstorm ＋ grill-me 共 15 項決定）
- 前一份規格：`docs/specs/2026-07-24-前端品牌重構-design.md`（視覺層，本輪沿用不推翻）
- 實作計畫：`docs/plan-ia-refactor.md`

---

## 1. 為什麼要改

上一輪把四頁換成 DIVE 品牌視覺，但**資訊架構原封不動**。使用者實際使用後的回饋是：

> 「跟我想像中的差的有點多。app 那頁應該要是情況概覽。設定方面有關什麼守門線的
> 都幫我拿掉，這邊應該就只需要留著系統設定就好。然後選題的部分這頁最嚴重，應該
> 要是我現在既有的主題可以讓我設定跟編輯選要每個主題要去哪裡抓資料，然後可以選
> 主題產內容。內容流水線那一個分頁很多餘，可以拿掉。」

歸納出三個結構性問題：

1. **選題頁不是選題的地方**。主題與來源設定被放在「設定」頁，選題頁只剩一顆
   「產生本週選題」按鈕。使用者心中的主體是**主題**，工具卻把主題藏在設定裡。
2. **抽象層擋在中間**。主題不直接連來源，而是透過 L1–L5 分層間接連。使用者要先
   記住「哪個來源屬於哪一層」才能設定，這層抽象沒有帶來對應的價值。
3. **概念比功能多**。守門線分數、常青／時效分類、五段流水線狀態，都是要使用者背
   在腦裡、但畫面上看不出差異的東西。

本輪的方針是 **拿掉抽象層、把主題放回主體位置**。

---

## 2. 本輪不做什麼（範圍紅線）

使用者在盤問中提出的產品方向：

> 「我覺得還要再新增說發到不同的社群（比如說 Threads、IG、LinkedIn 的會不一樣），
> 然後內容會先產出文字，然後再透過這些文字內容產貼文的圖。」

**這是下一輪的功能區，本輪明確不做**，經使用者確認。理由：要接圖片生成 API（多數
付費，與「只用免費額度」的既定成本策略衝突）、要改資料庫存多平台版本，需要獨立
一輪設計。

本輪的 `ideas.body` 欄位（單一份正文）保留不動，它就是未來「分平台文字」的前身。

## 4. 資料模型（改動後）

### 4.1 `themes` — 拿掉兩欄

```
themes(id, name, weekday, n_ideas)
```

- 移除 `kind`（決定 6）
- 移除 `source_layers`（決定 5）
- `weekday` 保留，但**只用於顯示**，不再控制任何按鈕能不能按（決定 7）

### 4.2 `sources` — 拿掉一欄

```
sources(id, name, url, fetch_type, enabled)
```

- 移除 `layer`（決定 5）
- `fetch_type` 合法值收成 `rss` ／ `search`（決定 14）

### 4.3 `theme_sources` — 新增關聯表

```
theme_sources(theme_id, source_id)   PRIMARY KEY (theme_id, source_id)
```

一個主題可綁多個來源、一個來源可被多個主題使用（多對多）。

### 4.4 `ideas` — 拿掉兩欄、新增一欄

```
ideas(id, theme_id, title, angle, source_url, status, body,
      created_at, published_at)
```

- 移除 `gate_score`、`gate_reason`（決定 3）
- 新增 `published_at TEXT`（可為 NULL；決定 12）

### 4.5 `performance` — 完全不動

`daibu/performance.py` 的 SQL 沒有用到 `kind`、`source_layers` 或守門線欄位，
本輪**後端一行都不改**。

## 5. 狀態機

```python
# daibu/pipeline.py
STATUSES = ["候選", "採用", "已發"]     # 畫面上看得到的三段
REJECTED = "已淘汰"                      # 隱藏狀態，只餵回 AI
ALL_STATUSES = STATUSES + [REJECTED]
```

- `set_status` 接受 `ALL_STATUSES`，其餘一律 `ValueError`
- 所有列表畫面只顯示 `STATUSES` 三段，`已淘汰` 永遠不出現在畫面上
- 狀態改為 `已發` 時，**同時寫入 `published_at`**；改離開已發時清成 NULL

### 舊狀態的搬遷

`草稿`、`已排程` 折進 `採用`。使用者目前的資料庫**沒有任何一筆**處於這兩種狀態，
但搬遷程式仍須處理，以免其他備份檔開不起來。

## 6. 抓取邏輯

### 6.1 `collector.collect(theme, sources)` 改成看綁定

```
舊：if theme.kind == "evergreen": return []
    再比對 source.layer in theme.source_layers

新：只取 theme.source_ids 指到、且 enabled 為真的來源
    theme.source_ids 為空 → 回傳空素材（不是錯誤）
```

**「沒綁來源」是合法狀態**，代表這個主題讓 AI 靠主題名自己發想（決定 6 取代了原本
的 evergreen 行為）。選題頁需在這種主題上顯示明確提示，避免使用者誤以為壞掉。

### 6.2 淘汰記憶

```python
prompt.build(theme_name, materials, n, avoid_titles)
selection.generate_for_theme(conn, theme, provider, sources)
    # 內部查出該主題所有 status = "已淘汰" 的標題，傳給 provider
```

- `avoid_titles` 為空時，prompt 不得出現空的「請避開」段落
- 只取**該主題**的淘汰紀錄，不跨主題污染
- prompt 不再有 `kind` 與 `gate_line` 參數

## 7. 頁面架構

側欄順序（檔名決定順序，設定移到最後）：

```
app.py              概覽
pages/1_選題.py      選題        ← 本輪主戰場
pages/2_成效.py      成效        ← 原 3_成效.py，只改號與文案
pages/3_設定.py      設定        ← 原 0_設定.py，大幅瘦身
（pages/2_流水線.py 刪除）
```

### 7.1 概覽（`app.py`）— 行動導向

由上而下：

1. **下一步提示**（單句，依優先序取第一個成立的）
   1. 有候選待決策 → 「你有 N 則候選等你決定」＋前往選題按鈕
   2. 有已採用但正文空白 → 「N 則已採用還沒寫正文」
   3. 今天排定的主題還沒產過候選 → 「今天排的是『X』，還沒產候選」
   4. 都沒有 → 「目前沒有待辦；下一個排定的是週三的『X』」
2. **三個待辦數字**：待你決策 ／ 已採用待寫 ／ 已發
3. **本週主題行事曆**：週一～週日七格，今天那格標示出來
4. **各主題近況表**：主題｜星期｜來源數｜候選｜已發｜平均互動
5. **需要處理的提醒**（有才顯示）：沒綁來源的主題、沒設 API key

「本週已發」在 `published_at` 補上後可誠實計算；舊資料沒有這個時間，顯示為未知，
不計入本週。

### 7.2 選題（`pages/1_選題.py`）— 主從式工作台

```
┌── 左欄（窄）─────────┬── 右欄（寬）────────────────────────┐
│ 我的主題              │ ▸ 主題設定（名稱／星期／每次產幾則）  │
│  ● AI 近期大事        │ ▸ 這個主題抓哪些來源（勾選清單）      │
│    週一 · 13 來源 · 0 │ ▸ ［產生候選］                        │
│  ● 本週熱門 Skill     │                                       │
│    週三 · 10 來源 · 0 │ 候選（N）                             │
│  ● AI 新創介紹        │  ┌─────────────────────────────────┐ │
│    週五 · 15 來源 · 6 │  │ 標題／切入角度／來源連結         │ │
│                       │  │ ［採用］［微調］［淘汰］          │ │
│ ＋ 新增主題           │  └─────────────────────────────────┘ │
│                       │                                       │
│ ▸ 來源庫（收合）      │ 已採用（N）— 可收合                   │
│                       │  點開可寫正文、可標記已發             │
└───────────────────────┴───────────────────────────────────────┘
```

- 左欄選中的主題存在 `st.session_state`；預設選第一個主題
- 候選與已採用**只顯示選中主題的**，不混雜其他主題
- 「來源庫」預設收合，展開後可新增／編輯／停用／刪除來源
- 主題沒綁任何來源時，右欄顯示提示：「這個主題沒綁來源，AI 會只靠主題名發想」
- 手機（375px）時左右欄堆疊成上下，主題清單在上

### 7.3 成效（`pages/2_成效.py`）

- 後端邏輯與版面**不動**
- 只改空狀態文案：「先到流水線把一張卡移到已發」→「先到選題頁把一則已採用標記為已發」

### 7.4 設定（`pages/3_設定.py`）

只留一個表單：LLM provider、模型、搜尋 provider、三個 API key。
移除守門線輸入框、主題管理區、來源白名單區。

## 8. 資料搬遷（就地升級，不刪檔）

`db.init_schema()` 需能認出舊結構並就地升級，且**可重複執行不出錯**。

1. `themes`：重建為 `(id, name, weekday, n_ideas)`，保留 id
2. `sources`：**先刪除 `fetch_type = 'manual'` 的來源**，再重建為
   `(id, name, url, fetch_type, enabled)`，保留 id
3. `theme_sources`：依**舊的** `themes.source_layers` × `sources.layer` 回填，
   已刪除的 manual 來源自然不會進來
4. `ideas`：重建為新結構，`草稿`／`已排程` → `採用`，`published_at` 給 NULL
5. `performance`：不動

### 搬遷後的實際數字（使用者目前的 `daibu.db`）

| 主題 | 舊分層 | 換算後來源數 |
|------|--------|--------------|
| AI 近期大事 | L1,L2,L3,L4 | **13** |
| 本週熱門 Claude/Codex Skill | L2,L4 | **10** |
| AI 新創介紹 | L1,L2,L4,L5 | **15** |

來源總數 18 → **15**（刪掉 TLDR AI、Ben's Bites、Awesome Claude Code）。

⚠️ **要讓使用者知道**：「AI 近期大事」原本靠 L3 的兩份電子報，而 L3 只有那兩個
manual 來源，刪掉後**該層變成 0 個來源**。這個主題實際能抓的來源比原本少。

現有 8 則題目（6 候選、1 採用、1 已發）與 1 筆成效**全部保留**。

## 10. 視覺（決定 15）

**沿用**：`daibu/theme.py` 的全部色票、Figtree ＋ Noto Sans TC、淺／深雙模式、
WCAG 對比度紅線、`prefers-reduced-motion` 處理。上一輪寫的 `tests/test_theme.py`
**一個都不准改**。

**調整**：資訊密度。主從式工作台要能一眼看到多個主題與候選，現行的
「官網首頁式」大留白會造成無止盡滾動。

- 首頁移除大尺寸 hero 吉祥物與大標，改成單行的「下一步提示」條
- 卡片內距與卡片間距各縮一級
- 左欄主題項目為緊湊列表，不是大卡片

**驗收**：桌機 1280×800 ／ 手機 375×812 各截圖兩輪，對照全域前端檢查清單逐項自評
（層次／留白／字體／配色／對齊／響應式／狀態／動效），375px 不得出現橫向捲軸。

- 不新增第五個分頁
